# D-041 — A Warden killed on the step the hero falls is a win, and the run has one outcome everywhere

- **Date:** 2026-11-10
- **Decider:** scheduler (delegated, D-009)
- **Class:** RULE (the rule is `boss.md` R-BOS-13; `combat_core.md` R-CMB-10 and `director.md` R-DIR-15 are reworded to it)
- **Status:** applied on `main` 2026-11-10 (branch `fix/d041-main`), carried to `dev/s2` and `dev/s3` by merge

## Context
Review entry #20 of `Validation/S3_review_fixes.md` (on `dev/s3`): a run that ends in death can still earn Win, the boss bonus and `Kill.Boss`, because the bank's recorder sees the Warden's kill while the run-over screen and `run_end` say death. The entry was deferred as a call about the award. The cause is on `main`, in how a run's end is ordered inside a step, and the award is only where it shows.

How a step was ordered before this record (`07_Technical §4`): Input, Hero, Enemies (the boss last), Weapons, Bullets, ResolveHits, Effects, Pickups, Director.
- A hit on the hero is dealt in Enemies and applied in the Hero phase of the next step (R-CMB-08). When it downs the last hero, `UDTHeroSubsystem` broadcasts `OnAllHeroesDown` there: the game mode ends the run as death, the boss system ends the fight with `boss_end{outcome: death}`, the director closes its block `ended_by: death`.
- The hull dies in ResolveHits. The boss system read that kill one step later, in its own Enemies phase, and only then ended the run as a victory.
- So the hero's death was always checked first, and two orders of the last two hit points both read as death:
  1. **Trade.** Both last hits are dealt on step N: the hull dies in ResolveHits of N, the hero's hit is applied in the Hero phase of N+1, before the boss system has read the kill. The Warden died a whole phase run before the hero, and the run read death.
  2. **Same step.** The hero goes down in the Hero phase of step N and the hull dies in ResolveHits of N, to fire already in the air.
- No spec line ordered the two. R-CMB-10 said the run ends with Death "the step every player's hero is down" and "Winning is the boss kill"; R-BOS-03 said the hull's death is one `Kill`; neither said which wins a shared step. `main` did not resolve it as a win anywhere.

`Dusktracer.Boss.RunEnd` (T-BOS-13) plays both orders in a game world with the game mode: before the change both read death in the game mode, `boss_end`, `dir_block` and `run_end` (15 assertions failed); the two controls (a death with the hull standing, a hull that falls one step after the death) read death and passed.

## Options
- A — Death wins the shared step, and the bank stops paying for a boss killed in a lost run. One outcome, but it takes the award from a player who finished the fight, and order 1 still reads as a loss with the Warden dead first.
- B — Leave the outcome as death and keep the award. The screen and the bank go on disagreeing: the defect.
- C — The Warden's death wins: a boss killed on the step the hero falls, or the step before a hit already dealt would down them, is a win in the sim, on the screen, in telemetry and in the bank.

## Decision
C. The player finished the fight; a trade on the last step should not read as a loss; and it makes the award true without taking anything from the player.

The smallest handling that keeps every other run as it was (`boss.md` R-BOS-13):
1. **The win is read before the hero's hits are applied.** The boss system reads the hull's kill at the top of the step after it (Input phase), not in its Enemies phase. It is the same step index a win was always read on, so no won run changes its length or its input stream. This settles order 1.
2. **A won run takes no hit.** From that read on (`FDTWorldView::bRunWon`), every hit on a hero is dropped as a dash drops it. In order 1 the hero stands at the HP they had; the sim keeps stepping on `main` after a run's end, and a hero can no longer fall under the victory banner.
3. **In the fight, a death ends the run after the step's kills.** While the hull stands, every hero down no longer ends the run from the Hero phase: the boss system holds it, stops the fight where the death found it, and after ResolveHits of that same step reads the kills. The hull killed: the run is won, and the death never ends it. The hull standing: the run ends by the death, in that step, with the records it always wrote. This settles order 2. The hero did fall there: `hero_down` is written and the hero stays down in a won run.
4. **The line is the step.** A hull that falls a step or more after the last hero is a death: the run was over. Outside a boss fight nothing moves: a death ends the run from the Hero phase as before (R-DIR-15).
5. **The screen.** `Hud.RunOver` is not drawn in a won run; `Hud.Victory` is. On `dev/s2` and `dev/s3` the run-over screen reads the game mode's win, which this decides, and needs no change.
6. **The bank (`dev/s3`).** `UDTRunRecorder` is not changed: the run now closes as `victory` in both orders, so Win, the boss bonus and `Kill.Boss` are paid on a run that reads as a win. A death with the hull standing pays none of them. Entry #20 is closed by the rule, not by a change to the award.

Not decided here: what a second player's fall means in co-op (`coop.md`, D-004, not written). The rule is written for "every hero down", which is what ends a run today.

## Hypothesis
We believe reading the Warden's death before the hero's hits, and a fight's death after the step's kills, makes both shared-step orders read `victory` in the game mode, `boss_end`, `dir_block` and `run_end` while no other run changes, because the win is read on the step it always was and a death outside those two orders ends the run on the step and with the records it always did. Measured by T-BOS-13 (both orders win, both controls die) and by seed 9107's `input_hash` on every arm the earlier records used, which must not move. Reverted if a hash moves for a reason other than a run that itself held one of the two orders, or if a human session reports a win that read as unearned.

## Result
- T-BOS-13 `Dusktracer.Boss.RunEnd`: failing before (both orders death), passing after; the controls pass before and after.
- Seed 9107 on `main`, `input_hash` unchanged: None `1c738e97`, Storm:Tempest `e96dc0a8`, Storm:ArcGrid `f8a90efe`, Storm:Downpour `5fa00d86`; RestartCheck is not a tool of `main` (it comes with `dev/s2`).
- On `dev/s2` and `dev/s3` the hashes are in the branch reports of the merge; the rule's test runs there unchanged. On `dev/s3` `Dusktracer.Meta.BossTrade` (T-MET-46) banks both orders as a win with the boss bonus and `Kill.Boss`, and a death with the hull standing with none of them.

## Impact (dependency sweep)
- Rules: `boss.md` R-BOS-13 added (T-BOS-13); `combat_core.md` R-CMB-10 says where a death's run end waits; `director.md` R-DIR-15 says the fight's fatal block is written after that step's kills are read. `07_Technical §4` gains the view field `bRunWon`.
- Code: `Boss/DTBossCore` (`ReadDefeat`), `Boss/DTBossSubsystem` (two more phase registrations, the hold), `Player/DTHeroSubsystem` (`HoldRunEnd`, `AnnounceAllDown`), `Player/DTHeroSim` (a won run takes no hit), `Game/DTHUD` (no death banner over a win), `Core/DTSimTypes.h`.
- Records of a death in the boss fight: the same lines with the same fields. `boss_end` and the fight's `dir_block` are written after that step's ResolveHits and not from its Hero phase; the director counts a step's kills in its own phase, which is later still, so the block's counts are what they were. Only a record another system writes between those two phases of the fatal step can now come before them.
- Records of a won run: `boss_end` comes before the Hero phase's records of its step, and a hit applied on that step is no longer in `hero_damaged` or `dmg_taken`.
- No constant, catalogue row or string moved. `number_change_log.csv` has no row.
- `Tools/`: nothing reads the order of the two log lines; `Run end reason=victory` and `Run end reason=death` are each still written once, and never both.

## Not verified
- No bot run or human run on record held either order: the rule is proven on a built scene (hits written into the view), not found in play. How often a real fight ends on a shared step is not measured.
- The HUD's banners are read through the game mode's flags in the test; no frame was drawn or looked at. On `dev/s2` and `dev/s3` the run-over screen was not opened in a launch for this: its reading of the same flags is from the code.
- Co-op (two heroes) is not built; the rule was tested with one hero.
- A frame-exact pause on the shared step (`S3_review_fixes.md` #8) was not combined with this.
- Since, on `dev/s3` (`fix/s3-verify`, `Validation/S3_verify.md`): the last two were taken up. Both orders with a Pause press, or a level-up hand, on the frame of the shared step end as a win and bank one (T-BOS-14). With two heroes the rule holds at the sim's level (T-BOS-15); the game mode starts one hero, so no two-hero run exists above the sim, and co-op is still not built.

## Swap-out point
Revisited when `coop.md` defines revive, or if sessions show wins on a shared step reading as unearned: the hold in point 3 can then be dropped on its own (order 2 becomes a death again) without touching points 1 and 2.
