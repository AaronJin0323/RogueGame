# D-058 — Draw code is the Visual module's by name, wherever it sits (amends D-055 item 1)

- **Date:** 2026-11-11
- **Decider:** scheduler (delegated, D-009). Drafted by the Visual module session on `plan/s4-wave2` (D-055 item 4); accepted on 2026-11-11 with the conditions at the end
- **Class:** PROCESS
- **Status:** applied (`AGENTS.md`); it amends D-055 item 1

## Context
D-055 item 1 draws the line between Mechanics and Visual at the folder `Source/Dusktracer/Presentation`. The code that draws is mostly elsewhere: every `*Renderer` file, the HUD, the XP bar, the pickup renderer, the draw half of `DTElite`, the boss bar's fill, and the `SimRender` bodies of the weapon, bullet, enemy, Keeper and gem subsystems, the hero and the director. Wave 1's packages B, D and F edited those files under D-043, before the modules existed. Every wave 2 package but two would edit a file D-055 gives to Mechanics.

## Options
A — ownership by name: a list of draw files and the `SimRender` bodies are Visual's; the files stay where they are. B — move draw code under `Presentation/`. C — a grant per edit.

## Decision
A. Visual's files, beside those of D-055 item 1: every `Source/Dusktracer/**/*Renderer.h` and `.cpp`; `Game/DTHUD.*`, `Game/DTHudLayout.*`, `Game/DTUIStyle.*`; `Progression/DTXPBar.*`; the boss bar's fill in `Boss/DTBossSubsystem.cpp`; the body of `SimRender` in any class, and the functions only it calls; `Debug/` files whose commands stage a frame and write no sim state (`DTDebugEnemyArt.cpp`, `DTDebugHeroArt.cpp`, `DTDebugArena.cpp`, and new ones of that kind); `Tests/Presentation/`; new presentation tools under `Tools/` that launch through `Tools/HiddenLaunch.ps1` (`EnemyArt.ps1`, `Frames.ps1`, `ImpactArt.ps1`). Such a tool takes a heavy-job slot as `07_Technical` R-TEC-18 has it (`Enter-DTHeavy` right after the processor mask) and adds its name to the entry lists of `Tools/tools_test.py`; those list entries are the only edit of that file a Visual job makes. The gate and launch scripts themselves (`Gate.ps1`, `Smoke.ps1`, `Perf.ps1`, `Machine.ps1`, `HiddenLaunch.ps1`, `contrast_check.py`) stay as `AGENTS.md` has them: changed only by a job the scheduler dispatches. A read-only getter on a sim class stays Mechanics' file and is added by a job the scheduler grants by name, with the seed 9107 proof first, as the hit and kill tap was. No file moves: a file moved on `dev/s4` exists on `main`, and every carry would conflict.

## Hypothesis
We believe a named list lets a visual package land without a grant per file and without a conflict between modules, because the list is the one `Tools/tools_test.py` already checks includes against; measured by D-055's own count of landings that need a conflict between modules resolved by hand; reverted to grants per edit if one such conflict is in a listed file.

## Impact (dependency sweep)
`AGENTS.md` and `12_Production §1` (the module table): the scheduler's. `Tools/tools_test.py`: a new launcher's name in its entry lists and nothing else; a later job may make the list of presentation headers one constant shared by the check and the record.

## Accepted with these conditions (scheduler, 2026-11-11)
1. An edit by the Visual module in a file outside `Presentation/` stays inside draw code and adds no state the sim reads or writes. R-PRE-11 and the include check of `Tools/tools_test.py` are the tests, and a package's sim proof is read at every hand-over as before.
2. The Visual module works on `dev/s4`. A draw-code defect that also exists on an earlier branch is reported to the scheduler, who places the fix on the lowest branch that has it (D-050 item 3) and names who makes it.
3. At a carry, a conflict in a listed file keeps both sides' behaviour, is named in the carry note, and is looked over by the Visual session before the leg lands.
4. Text stays where it is: string tables and the specs of the systems are not on this list.
