# D-010 — Palette generated into code; enemy hull token; fallback registry

- **Date:** 2026-10-30
- **Decider:** scheduler (delegated, D-009)
- **Class:** RULE
- **Status:** applied

## Context
The bullet and enemy agents each copied hex values from `04_Presentation §3` into C++ because no shared token source existed (R-PRE-09 forbids that); the enemy hull borrowed `Pal.UI.Panel`. Both agents' material fallbacks were unregistered (R-TEC-05) because `09_Catalog` was empty.

## Decision
- `Tools/gen_constants.py` also generates `Source/Dusktracer/Core/DTPaletteGen.h` (`DTPal::<Group>_<Name>` as `constexpr FColor`) from the §3 table; the doc stays the single source. Its `--check` (gate step `constants`) fails on a stale header or on any colour literal in `Source/` outside generated files (T-PRE-09).
- New token `Pal.Enemy.Body` #1C1E24 (dark gunmetal hull). The hull is a silhouette; enemy readability is carried by `Pal.Enemy.Optic` under R-PRE-05.
- `Docs/09_Catalog/fallbacks.csv` registers every `Fallback_*` code path with its replacement and trigger; `Tools/docs_lint.py` check 9 keeps code and registry in step (T-TEC-05).

## Hypothesis
We believe generating tokens removes palette drift between docs and code; measured by the `constants` gate step staying green across S1 art passes.

## Impact
- `04_Presentation` R-PRE-09/T-PRE-09, §3 (new row); `07_Technical` T-TEC-05
- `Combat/DTBulletSubsystem.cpp`, `Enemies/DTEnemySubsystem.cpp` read `DTPal::`
- `02_Systems/enemies.md` §Data and §Open
