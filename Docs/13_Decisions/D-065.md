# D-065 — A packaged Shipping game that crashes ends: no in-process minidump and no crash folder by default

- **Date:** 2026-11-11
- **Decider:** scheduler (delegated, D-009), on the Mechanics module session's reading and options (`Validation/S1_crash_exit.md`)
- **Class:** BUG (`package.md` R-PKG-16, T-PKG-16), with one choice of default
- **Status:** applied on `main` (`s1/crash-exit`); the session A package is rebuilt with it

## Context
The package checks on `dev/s3` found a crashed Development game still alive after 180 s. Read on `main`'s code by the Mechanics session, on this PC, on the hidden desktop:

- A packaged game hangs after a crash when the crash meets busy threads. With sound on: 5 to 8 of 10 crashed Development launches and 3 to 5 of 10 Shipping crashes right after a run starts; 0 of 20 Shipping crashes three seconds into a run. With sound off and `-unattended`: 0 of 40, and another launch line (a map first, `-nopause`) brings it back, 5 of 10.
- In every hung launch the one live thread is the engine's crash reporting thread inside `MiniDumpWriteDump`, which the engine calls in process; the game, render and audio threads are suspended, the crash context is whole and the dump is 0 bytes.
- A packaged exe holds no dialog template, so no crash dialog can appear: a tester sees the game close, or freeze.
- No ini key and no launch argument reaches that path in a packaged game. A smaller dump (`MinidumpIncludeReferencedMemory=0`) hangs as often. A watchdog thread inside the game would be suspended with the rest.
- No crash is known in S1. The validators' launchers pass neither `-nosound` nor `-unattended`, so a tester whose game did crash could meet the freeze.

## Options
- A — A kit line only: the host waits fifteen seconds and ends the game in Task Manager. A tester sits in front of a dead full-screen window about as often as not.
- B — Shipping writes no in-process minidump and no crash folder by default; an argument restores the engine's path for a diagnosis.
- C — The same, only behind an argument the launchers pass. A person who starts the exe directly still meets the freeze.
- D — Keep the crash context and skip only the dump. Not built: the context names the Windows user and the machine, and R-PKG-02 promises that a Shipping build writes nothing that can.

## Decision
B.

1. A Shipping build sets the engine's two switches at the game module's start: the crash reporter path is off and the minidump has no file to open. A crashed game then ends in about two seconds and writes nothing beyond its run file. `-DTCrashDump` restores the engine's path for a developer.
2. Any other packaged build (the Development proof build) keeps the engine's path, so the redaction check of `dev/s3` (R-PKG-11, T-PKG-15) still has a crash folder to read, and takes `-DTCrashNoDump` when a check needs only that the process ends.
3. The run file is the same with and without the fix: whole up to its last flush, with no `run_end` when the crash came before one.
4. The kit keeps its line for a frozen game: the fix does not cover a crash before the game module loads, and every reading is this one PC's.

Why B and not D: what a crash leaves on a tester's PC would name them, and the one promise the package makes to a tester is that it does not. Why not C: the default should be safe for every way the game is started.

## Hypothesis
We believe switching the in-process minidump off moves the share of crashed packaged launches that end by themselves from about half (at a busy moment, with sound) to all, because the stall is inside the dump's own writer; measured by `Tools/CrashExitCheck.ps1` (T-PKG-16): with the fix, Shipping early fatal error 20 of 20 ended and early null write 10 of 10, Development with the argument 20 of 20, against 5 of 10 hung in each control on the same packages; reverted, the two assignments removed, if a later engine version writes its dump out of process, or if a diagnosis ever needs dumps from testers and a way to write them safely exists.

## Impact (dependency sweep)
- Rules: + R-PKG-16, T-PKG-16 (`package.md`). R-PKG-02 is now true for a crash as well.
- Files: `Source/Dusktracer/Dusktracer.cpp` (17 lines, packaged Windows builds only, never an editor), `Tools/CrashExitCheck.ps1`, `Tools/crash_exit.py`, tools tests, `Validation/S1_crash_exit.md`.
- The session A package is rebuilt: this is a defect a validator would meet (D-055 item 9).
- What a tester's PC no longer keeps after a crash: `Saved\Crashes\UECC-...` (the crash context, a small ini, a dump of 1 to 4 MB). The export only ever took it with `-IncludeLogs`.
- Cost: a validator's crash leaves no dump and no callstack. The seed in the run file's name replays the start; a person's inputs are not recorded.
- Carried forward with the next carry. On `dev/s3` CrashExportCheck still crashes the proof build on the engine's path and so still meets the hang (5 to 9 of 10 here); making that check robust is a job of its own.
- Not tested: a real audio device on a visible desktop; other PCs; a crash before the game module loads; Shipping without the throwaway crash switch (T-PKG-16 runs on Development).

## Swap-out point
An engine version that writes its dump out of process, or a decision to collect crash reports.
