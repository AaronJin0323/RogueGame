# D-037 — A gate check reads every run it launches, and a pool check has to be able to tell the pools apart

- **Date:** 2026-11-10
- **Decider:** scheduler (delegated, D-009)
- **Class:** RULE
- **Status:** applied

## Context
The review of `dev/s3` at `5ccf82e` left two confirmed majors deferred, each for a call (`Validation/S3_review_fixes.md` #94, #64). Both are about what a gate step's PASS means, so one record holds them.

- **#94.** The `firstrun` step launches six runs (three S1 Keepers, seeds 9100 and 9101, the first-run pool) and reads R-OFF-15 with `-Check T-OFF-15`. T-OFF-15 judges the runs that reached `C.RUN.LENGTH_TO_BOSS` and drops the rest, which is right for a battery where deaths are data. On the gate it means five runs could die early and the step would read `PASS (1/1 runs at the boss)`, with a whole Keeper unread.
- **#64.** `Tools/MetaCheck.ps1` played every launch for 20 s: two hands, the Patron hand and the first Level hand. Its three pool readings (G: a profile bought back up to the tool pool plays as a tool run; H: the first-run pool holds no locked card; I: a met Keeper's Keys are in and its Amps shut) rested on those two hands. Measured here on seed 9108: the first Level hand does differ between the tool pool and the first-run pool (two first-run locks are dealt), so the step was not blind, but no pool deals an Amp or a Trait before a Key is held, and none can be held by the second hand. "No Amp in a hand" was true of every pool, and the hash comparison of G never played a hand the nine branch nodes could have changed. `S3_tree.md` and `S3_doors.md` claimed the step showed both.

## Options
#94:
- A — Leave it and say so in `11_Quality`. A gate step that can pass on one run of six is not the six-run reading its row names.
- B — A least count per arm (one run of each Keeper at the boss). It still lets half the battery go unread, and which half is whatever died.
- C — Every launched run is read. A run with no record, no folder, or an end short of the boss fails the check. Only where asked for (`-ReadAll`): other batteries keep T-OFF-15 as it is.
- D — As C, but an unread run makes the step NOT RUN. The gate then prints `GATE: PASS (n not run)` over a first pool nobody read, which is how this was missed.

#64:
- A — Narrow the two notes to what 20 s shows and add the long version as a script outside the gate.
- B — Make the check real: play the pool launches long enough to deal the cards in question, read the cards dealt from the telemetry, and require a control to have shown them. Preferred if it costs under about two minutes of gate time.

## Decision
**#94: C.** `Tools/BotRuns.ps1 -ReadAll` counts the runs it launched and hands the count to `Tools/bot_summary.py --read-all <n>`; T-OFF-15 then fails unless each of the n is a Steered run read at the boss, and its line names every unread run with its outcome and end time. The gate's `firstrun` step passes `-ReadAll`, so its required count is six of six. A run lost to a machine fault fails the step; it is rerun once and said so, as any odd failure on this PC is. If a change to the game makes one of these six seeds die short of the boss, the step fails and stays failed until someone reads why: that is a first-run reading, not noise, and picking new seeds is a change to the step made in the open.

**#64: B.** A full run costs little more wall time than a 20 s one, because launch time dominates. The pool launches of G, H and I play `-PoolSeconds` (600 s) of sim time at bot skill 1.0, where the bot is alive at the cut, so the run ends on the cut and its step count is exact (a death's last step is not, `S3_doors.md`). `Tools/pool_read.py` reads the `offer` and `offer_pick` records:
- **G** (`same`): the gated profile is dealt the tool run's hands card for card and takes the same picks, over at least `-PoolHands` (12) hands, besides the equal input hash, steps and CSV; both runs end on the cut.
- **H** (`first`): the first-run pool shows no Tree-locked id (any id a node of `tree.csv` unlocks, or a row of `first_run_locked.csv`) over at least 12 hands.
- **I** (`met`): on a copy of the door's save, the run chooses Radiance, takes a Radiance Key, and no Amp, Trait or Path row of Radiance is dealt, with at least `-KeyHands` (8) hands dealt after the first Key.
- **The control.** One more tool launch of the same seed and length (P), and one that chooses Radiance. G and H fail unless P was dealt Tree-locked modifiers and Tree-locked blessing cards; I fails unless the Radiance tool run was dealt Radiance's. A window that cannot tell the pools apart reads FAIL, `cannot tell the pools apart`, never PASS.
The save steps (A to F, and I's seat readings) keep 20 s: they read the file and the log, not the pool. The hand counts are tool parameters with slack under the readings (19, 21 and 17), not game numbers.

## Hypothesis
We believe the `meta` step now fails for a pool that differs from a tool run's in any card a 600 s Storm or Radiance run is dealt, and the `firstrun` step for any of its six runs going unread, because both now assert on what was dealt and count what was launched. Measured by the `ReadAll` and `PoolRead` classes of `Tools/tools_test.py`, and on real launches: `-PoolSeconds 20` reads FAIL on all three pool readings, the 600 s step reads PASS with 19 hands the same, 0 Tree-locked ids in 21 first-pool hands, and 17 hands after the first Radiance Key. Revisited if the step's added time (26 s on one reading, 162 s against 136 s) grows past two minutes, or if a balance change moves the bot's death inside the window.
