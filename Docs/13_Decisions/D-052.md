# D-052 — Tool runs keep off logical processors 0 and 10 of this PC, and the gate proves the rest on every run

- **Date:** 2026-11-11
- **Decider:** scheduler (delegated, D-009)
- **Class:** RULE (method)
- **Status:** decided 2026-11-11. The mask file is in place on this PC and `AGENTS.md` carries the hand rule. The tool half (every Tools script applies the mask; a `cpu` gate step) is part of the job `s1/gate-main`

## Context
`Validation/S4_py_fault.md` (read on `dev/s4` 92ce1a5; the note is on `main`), `Validation/plans_audit.md` 4.1, `OPEN.md` O-012.

- The `tools` step of the gate on `dev/s4` died on most runs in two art checks. The last gate there passed with that step skipped and read apart on the sixth try.
- The fault follows the logical processor, not the code. Pinned to processor 0 the two checks die on 16 to 20 of 20 runs. Processor 10 faults when the machine is idle. On every other processor (1 to 9, 11 to 15, the E-cores) none of 351 runs faulted.
- A ten-line loop of float sums, with nothing unusual in it, dies 17 of 20 times on processor 0 and 0 of 20 on processor 2. Three Python builds fault alike (3.14.4, the engine's 3.11.8, Blender's 3.13.13). No interpreter setting changes the rate. The two art checks only stand out because they are the longest stretch of pure bytecode in the gate.
- Processors 1 and 11 share their physical cores with 0 and 10 and never faulted. So the silicon of those cores is not shown to be at fault: firmware, or a driver whose interrupts land on 0 and 10, fits as well. Nothing that can be run from Python tells them apart. Microcode is 0x12F, BIOS 1820.
- The engine, the compiler and the bot batteries run on the same processors. STATE has long said "rerun an odd failure once"; the audit's point stands that this trains agents to discount real intermittent bugs and that a wrong PASS cannot be told from a real one.
- The previous readings were taken on all 32 logical processors. Seed 9107 has hashed the same through many gates, which says the sim's results repeat; it does not say every build and package was sound.

## Options
- A — An affinity mask on the gate's Python steps only. Fixes the step that showed the fault and leaves builds, tests, bots and packages on the two processors.
- B — An affinity mask on every tool run, kept in a file on the machine, with a check in the gate that the processors left in are sound.
- C — A retry that prints its try count. At idle about 19 of 20 runs die, and a retry cannot catch a wrong answer that does not crash.
- D — Pin an interpreter. Three versions fault alike.
- E — Fix the PC. Only the owner can (O-012), and it is the only option that also covers the game the owner launches by hand.

## Decision
B now; E stays with the owner as O-012, with the evidence.

1. **The mask is a fact about one machine and lives on it.** The file `<git common dir>\dt-locks\affinity.txt` holds one hexadecimal mask on one line. A machine without the file runs unmasked. On this PC it reads `FFFFFBFE`: every logical processor but 0 and 10. The sibling threads stay in because 351 runs say they are sound and the check of item 3 watches them.
2. **Every Tools script that starts work applies it first**, so the compiler, the engine, the bots and Python all inherit it. One helper holds the code; `Tools/tools_test.py` proves a child process sees the mask. Until that lands, an agent sets the mask by hand at the start of each command (`AGENTS.md`, Known traps).
3. **The gate gains a first step, `cpu`.** It runs the reduced loop of `S4_py_fault.md` pinned to each processor the mask leaves in and fails the gate if one faults, naming it. The step's size is calibrated on processor 0, which must fail it at least 19 times in 20; that calibration is a reading in the job's note and never a gate step. The `GATE:` line prints the mask it ran under.
4. **An odd failure is still rerun once, and is now reported every time** with both results and the processors it ran on. Under the mask there should be none, so each one is evidence and goes to STATE.
5. **Readings taken before the mask stand as they are** and say so where they are cited. A reading that an exit or a decision rests on is retaken under the mask when its job next runs: the S1 package, the perf reading, the exit batteries.

## Hypothesis
We believe running every tool inside the mask moves odd failures (a gate step rerun, a compile that faults, a gate that passes on the sixth try) from most `dev/s4` gates to none, because every fault traced so far followed processors 0 and 10; measured by the count of reruns reported over the next twenty gates on any branch and by the `cpu` step's line on each; reverted, by deleting the mask file, when the owner's fix makes processors 0 and 10 pass the `cpu` step's loop 20 times in 20.

## Impact (dependency sweep)
- Rules replaced: STATE's line "rerun an odd failure once before calling it real" becomes item 4. `11_Quality §1` gains the `cpu` step and `07_Technical §8` its risk row, both in the job.
- Constants: none. The mask is machine data, not a tuned value, and is not in the repository.
- Files: `AGENTS.md` (Known traps), `13_Decisions/OPEN.md` (O-012 rewritten with the evidence), `STATE.md`; in the job, a helper under `Tools/`, the first lines of every Tools entry script, `Tools/cpu_canary.py`, `Tools/Gate.ps1`, `Tools/tools_test.py`.
- Not covered: `Tools\Play.bat` and a packaged build run by a person use every processor, on this PC or any other. Only O-012 covers that.

## Swap-out point
The owner's fix of the PC (O-012). If the `cpu` step ever names a third processor, the mask grows by that processor the same day and O-012 is told.
