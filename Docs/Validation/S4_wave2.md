# S4 wave 2: what comes after wave 1, and what it waits for

For the scheduler. A plan, written by the Visual module session on `plan/s4-wave2` from `dev/s4` at fc5000b (D-055 item 9: "A module session may plan held work; it does not build it"). It starts nothing. Nothing was built, launched or measured for it. Every number is quoted from a note on `dev/s4` or from `STATE.md` on `main`, and §7 says what was not checked. D-055 and `OPEN.md` O-015 are cited from `main`: `dev/s4` at fc5000b does not hold them.

Rows are cited from `Validation/S4_artbook_gaps.md` as section and position, as `Validation/S4_wave1.md` does: "§2.3 r26" is the 26th row of the table in that note's §2.3. Sizes are that note's, for one session: S 0.5 d, M 1.5 d, L 4 d, XL 7 d at the midpoints `S4_wave1.md` §3 used.

## 1. Where wave 1 leaves the screen

Wave 1 named 53 of the 212 rows. With package E merged, the shapes are drawn: the plate and its apron, four role hulls, the hero's figure, tracers, the HUD, and a hit and a kill. What is still not drawn is **state**. A player cannot see that an enemy is Shocked, Burning, Chilled or Marked except through three flat Frozen cues (`04_Presentation` R-PRE-11). The six weapons that are not plain rounds (§2.3 r5 to r9 and r12) still draw their grey-box shapes. Gems and chests are cubes. Elite parts were placed for a cube and float clear of the new hulls (`S4_b_enemies.md` §2). Every one of those is something the sim already knows and the screen does not say.

So the proposal for wave 2 is **state before surface**: draw every sim state a player has to read, at the same silhouette grade as wave 1, before any row is deepened with texture or fine detail. The reasons:

- Surface depends on calls that people have not made: the frame (D-036 reverts to 2000 uu on one validator's report, and detail under about 5 px at 27 px/m is held by D-043), the hull rule (D-010), the floor target (O-014). State does not: a Burn layer reads the same at either frame, on either hull.
- State is what the game is about. The Keepers' statuses and the weapons' shapes are the build the player made; today the build is visible only in the trail colour and on the HUD.
- State rows were held for one reason only: "Needs real hulls or the per-step tap first (wave 1 builds those)" (`S4_wave1.md` §4). Wave 1 built both.

## 2. The tests for a row

The four tests of `S4_wave1.md` §1 stand: (a) no open human reading under it, (b) no sim number and no rule moves, (c) no AI-sourced or downloaded asset, generated by a script in this repo, (d) checked without a window. Wave 2 adds two, both learned in wave 1:

- **(e) Read through a tap.** A row that needs sim state no presentation code can read today names the read-only getter or tap it needs, and that getter is its own first job with the seed 9107 proof, as the hit and kill tap was (D-055 item 6). Presentation never reaches into a sim array to work around a missing getter.
- **(f) Owned files only.** A row names every file it edits. A file outside the Visual module (D-055 item 1) is edited only under the grant of §5 item 2 or by the owning module.

Session A reads `main`, the S1 build, which has none of wave 1's art. So a row passes (a) only if what session A can say about the frame, a token or a readability rule cannot undo it. A reading that needs a person to look at `dev/s4` itself is listed in §6 and is not session A's.
